# KPF-64 F/FB successor runtime planning

The original FB partial contains 86 successful eligible requests, not a complete arm: 1,880,162 prompt tokens, 6,742 generated tokens, 14,334.6 seconds wall span and 52,933.4 seconds summed per-request service. The retained, newly narrowed 230-request cohort appeared in the original F run, where its records total 6,686,517 prompt tokens and 19,947 generated tokens. The old F had 37 additional requests, and the FB run was interrupted; neither is a valid substitute for a fresh matched arm.

`runtime-budget-20261102.json` is a **capacity estimate**, recomputed from these original JSONL bytes and the file-verified successor, not an inference result or a guaranteed completion bound. Both source-record SHA-256s and the successor report/manifest hashes are inside it. `runtime_budget.py` emits no prompt or model output; it refuses missing F coverage, duplicate or failed eligible rows, invalid timings, and successor hash drift.

- The no-cache conditional proxy assumes FB must prefill all **6,686,517** historical F prompt tokens, and generate the historical F **19,947** tokens. Dividing those by the FB partial's service-weighted rates (105.21 prompt tokens/s and 0.1923 generated tokens/s) gives **46.47 summed service-hours**. The prompt and generation components add because they were recorded separately in each response. This total is not a measured FB wall time; concurrent service counters overlap and future live histories can differ.
- An intentionally cautious **192-hour (8-day) proposed uninterrupted FB window** uses four times that serial proxy, plus the maximum 60-second gap for every one of the 230 requests and 30 minutes for startup/cleanup, rounded up to a whole day. Four is an explicit engineering planning margin, not a fitted percentile, scientific threshold, or guarantee. A separate capped-token stress scenario uses each observed maximum per-token service cost for all 230 requests, 65,536 prompt tokens and 128 generated tokens per request, 60-second gaps and a 10% margin: **441 hours**. Both numbers are scenario estimates: the 86 observations are not a random or complete FB cohort, future scheduler/model behavior can be slower, and a longer window cannot ensure successful coverage. The 7,200-second network timeout is a socket operation timeout, not proof of a total request or arm deadline.
- A fresh F arm is also needed. The original F's 1.74-hour elapsed span was generated by the larger 267-request workload and is not a matched successor result or a guarantee. The owner must plan its window independently and preserve the exact same successor manifest and exposure record in both arms.

The prior repeated 4-hour atomic FB grants and 15.8-hour extrapolation do not size this changed cohort. If an 8-day uninterrupted 24-core grant cannot be provided, first design and validate a **state-preserving** continuation that preserves slot/cache contents, live generated histories, burst/think scheduling and raw attempt custody. Simply skipping completed JSONL rows after restarting the server loses cache state and does not establish equivalence. No resume implementation, grant, inference run, changed statistical test or promotion is authorized by this estimate. A cutoff remains incomplete; do not silently replay exposed requests.

To reproduce with the original private cohort and source records, use the command in `family_successor.py` to materialize/verify the successor, then invoke `runtime_budget.py --help` with its predeclared report and manifest hashes plus the retained F and FB request files. The sample output is public aggregate metadata only; the input transcripts and raw model responses remain private.
