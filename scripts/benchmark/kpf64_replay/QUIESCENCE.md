# KPF-64 experimental cooperative quiescence

`replay_driver.py --pause-control-socket /private/dir/control.sock` enables an **experimental, default-off** local control. The parent directory must already be private (0700) and owned by the process UID; the socket is mode 0600. Commands are JSON objects, each on one connection: `{"op":"pause","timeout_s":30}`, `{"op":"status"}`, `{"op":"resume"}`. A successful `pause` waits for the driver's in-flight completion calls **and** slot/metrics reads to finish, blocks new calls, and reports `quiescent`; timeout returns `ok:false` and unblocks the run. Paused time does not consume the remaining simulated think gap. Existing behavior is unchanged when the option is omitted.

This is a building block, **not a cross-grant launcher or authority to release a region**. It does not pause or verify the llama-server process, preserve its RAM reservation, establish that slots/cache are unchanged, freeze the driver, bind PID births, own or extend a grant, or guarantee completion before a hard deadline. A safe supervisor must hold its current CPU/RAM grants while requesting quiescence; verify that all owned requests and server work have actually drained; freeze the captured, identity-verified driver and server; confirm both are stopped before releasing CPU; retain a valid RAM reservation while they remain live; reacquire a matching CPU claim before resuming both; then send `resume`. If the drain cannot complete before cutoff, it must fail closed, preserve the exposed/incomplete run and not silently retry those units. Stopping only the driver and restarting the server loses cache state and does not satisfy this condition. Real server freeze/resume parity, resource accounting, crash recovery and timing/scheduling equivalence are still required before use in a KPF-64 arm.

The tests cover draining/blocking, timeout rollback, exclusion of paused time from think waits, private socket handling, and SIGSTOP/SIGCONT of the driver's *in-process fake server* while preserving a stub slot. That test demonstrates a local process behavior only; it does not establish native llama-server cache preservation or grant compliance. Do not use it as an inference or performance result.
