## AK-ASM-I8GEMM-PERCHANNEL-GEMV (proposed) -- per-row int8 weights for the bandwidth-bound 27B verify GEMV
Box: `handoffs/active/autokernel-loop.md:4343` (AK-ASM-I8GEMM-PERCHANNEL-GEMV). Citation: intake-2828#record (AITER
per-channel 8-bit weight GEMMs). **Prior negative that bears on it:** `akm-i8gemm-perchannel-prefill` (0.821x, 68.5 vs
83.3 TFLOP/s at m5120 n2048 k6144, row ak-asm-i8gemm-perchannel-gpu-20261122) measured only the compute-bound prefill
route (dispatch ne11 >= 129); the verify GEMV is memory-bound and judged in GB/s, so that negative does not transfer
and this entry must not be read as re-proposing the prefill port. The weight half already passed 27B KLD 0.001015, dPPL
+0.082% (AK-ASM-I8GEMM-PERCHANNEL-KLD).
**Mechanism:** on trace ak-c18-27b-df2-v5i-trace-gpu-20261122, `q8mf6_mul_mat` is 25.2 of 40.07 ms (62.9%) per 27B
DFlash2 verify at 1071 GB/s (71% of the 1.498 TB/s measured peak). A dense per-row layout (32 B per 32 weights plus one
scale per row, vs Q8_0's 34 B) reads 1/17 (5.9%) fewer weight bytes and drops the per-block scale load.
**Question:** does the per-row layout cut q8mf6 time at n=2..8 in proportion to the bytes saved? Confidence is low: at
71% of peak the kernel is not purely byte-bound.
**Step 1 (no GPU):** from the C19 mmq-q8-mf.cu record, how MF_INPLACE streams per-block scales and the bytes per weight
q8mf6 reads; ceiling = bytes saved / bytes streamed x q8mf6 share of verify. Pure byte arithmetic gives
0.059 x 0.629 = 3.7% of verify, barely over the 3% bar, so any non-byte-bound share kills it.
**Step 2:** speed-of-light knob timing of the per-row layout inside q8mf6 at n=8 (rocprofv3, paired), then, at >= 3% of
verify, an e2e KEEP/DROP; 27B KLD <= 0.003 already cleared for the weights.
**Stop rules:** stop-on-answer at the step-1 ceiling or the step-2 verdict. **Falsifier:** step-1 ceiling < 3% of verify,
or the speed-of-light knob saves < 3% of q8mf6 at n=8 -- close.

## MMID-HELPER-READLANE (proposed) -- wave-uniform `__shfl_sync` in the mm_ids helper as `__builtin_amdgcn_readlane`
Box: `handoffs/active/kernel-champion-and-promotion.md:1876` (MMID-HELPER-READLANE; arm of the MMID-HELPER-N10-GATE build,
no separate row). Citations: intake-2825#02, intake-2825#03.
**Mechanism:** the served mm_ids helper (ggml/src/ggml-cuda/mmid.cu:92 @ a6a32c1) uses one `__shfl_sync` whose source
lane is wave-uniform; on gfx90a a shuffle goes through ds_bpermute (LDS crossbar, lgkmcnt wait) while `readlane` is a
scalar-path op. The helper is 7.33% of Q38FN pp2048 GPU time, so a 3% helper gain is about 0.2% end to end: this is a
small lever and only worth the arm because the gate build already exists.
**Question:** does the readlane arm change the ISA (instruction count, VGPRs) and the helper us/call?
**Step 1 (no GPU):** build the arm, record the ISA diff (`gfx90a_isa_audit.py diff`) under the box, add the arm to the
MMID-HELPER-N10-GATE row argv.
**Stop rules:** stop at step 1 if the ISA is unchanged (the compiler already emitted readlane). Otherwise the gate
row's helper us/call decides: KEEP at >= 3% helper gain, else DROP.
**Falsifier:** identical ISA, or helper gain < 3% in the gate row -- close.
**Follow-on (no checkbox, same box section):** at gate close, if the helper is still >= 3% of Q38FN pp2048 after the
fold, port the mbcnt-based ballot rank (upstream #32841 shape) to any ballot site that remains.

## RKA-TRACE-SHARES-1 (proposed) -- two upstream-port questions answered from existing traces and arithmetic
Box: `handoffs/active/rocm-kernel-authoring.md:2625` (RKA-TRACE-SHARES-1). Citations: intake-2826#04 (part a),
intake-2840#00 and intake-2840#01 (part b).
**(a) Mask-to-KV-max share.** `flash_attn_mask_to_KV_max` launches only when Q->ne[1] >= 1024 or ne[3] > 1
(fattn-common.cuh:1493 @ a6a32c1). **Question:** what share of prefill GPU time does it take on the served 27B and
Q38FN traces? **Falsifier:** share < 1% -- close the ballot-reduce port.
**(b) Chunk imbalance under uniform splits.** In the gv GQA-verify kernel (fattn-gqa-verify.cu:769-781 @ a6a32c1) KV is
split uniformly across blocks. **Question:** for np4 KV-length mixes, padded and unified layouts, what is max/mean live
KV chunks per block per gv verify block? Pure arithmetic from recorded slot lengths. **Falsifier:** max/mean <= 1.15
closes the min-max planner idea; > 1.3 files one GPU row (between 1.15 and 1.3 is a judgment call recorded under the box).
**Stop rules:** stop-on-answer when both numbers are recorded with trace paths; no GPU, no kernel edit.

## TOK-BPE-TIME-1 (proposed) -- vocab-only tokenize time of a 100k-token prompt vs cached-turn TTFT
Box: `handoffs/active/cpu-decode-roofline-program.md:105` (TOK-BPE-TIME-1). Citations: intake-2829#00, intake-2829#04,
intake-2829#05 (upstream #32859 zero-alloc BPE).
**Question:** how long does the current BPE tokenizer take on one real 100k-token orchestrator prompt on the Qwen3.8-27B
and Qwen3.6-35B-A3B vocabs (vocab only, no weights, one core, seconds, at C19 a6a32c1), and what share of the
cached-turn TTFT of the same roles (from existing rows) is that?
**Expected:** unknown; cached turns skip prefill, so tokenization is the one cost that scales with the full prompt.
**Stop rules:** stop-on-answer when both vocabs have a repeated timing; use existing TTFT rows only.
**Falsifier:** tokenization < 2% of cached-turn TTFT -- close the #32859 port. At >= 2%, port as one commit on an
experimental branch after upstream human review, with test-tokenizer-0 for qwen2 and qwen35 and a token-id diff on 20
real prompts.

## SPEC-COPY-COV-1 (proposed) -- exact longest-suffix copy-match coverage before any copy-proposal drafter work
Box: `handoffs/active/speculative-decoding.md:871` (SPEC-COPY-COV-1). Citations: intake-2847#00, intake-2847#01,
intake-2832#00, intake-2832#01.
**Mechanism:** our ngram-mod (common/speculative.cpp:2651-2812 @ a6a32c1) is a hashed fixed-n window, not
longest-suffix, so it under-reports what an exact copy index would propose.
**Question:** over archived COPYSPEC P1 outputs (`artifacts/copyspec-20261006/source-archive/results/P.jsonl`, 85
requests), build an exact longest-suffix index and report per position the match length and whether the next 3 tokens
agree, for code and prose, in-sample and leave-one-out (the in-sample number alone overstates coverage).
**Stop rules:** stop-on-answer when the coverage table (code, prose, in-sample, leave-one-out) is recorded; offline, no GPU.
**Falsifier:** positions with match length >= 5 and >= 3 agreed tokens are < 5% on code and < 2% on prose -- close the
copy-proposal path. Above threshold fires the trigger on the box: an exact longest-match index as proposal source for a
default-off training-free copy-proposal probe on the DFlash2 weights (one GPU row).
